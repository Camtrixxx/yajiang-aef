# 实验记录：v1.2 训练加速

## 1. 结论

8 卡 A800，`configs/yajiang_v1_2.yaml`：

| 指标 | 基线 | 优化后 | 倍率 |
| --- | ---: | ---: | ---: |
| Step 时间 | 606.4 ms | 350.2 ms | **1.73×** |
| Epoch 时间 | 37.7 s | 20.1 s | **1.88×** |
| 峰值显存 | 44.57 GB | 20.86 GB | **−53%** |

按 epoch 时间折算，200 epoch 训练从约 2.1 小时降到约 1.1 小时。

已通过真实入口 `scripts/train_with_manifest.py` 跑完 2 epoch 端到端验证：loss
4.11 → 3.36 正常下降，`best/latest/final.pt` 与 deploy 模型均正常写出，每个
checkpoint 240 个 key、0 个污染 key、`strict=True` 可加载。

分支：`perf/training-acceleration`（10 个 commit）。

## 2. 五项改动

五项独立测得的倍率**不能相乘**——compile 与 fast_attention 有重叠，num_workers
优化的是前几项暴露出来的新瓶颈。1.88× 是端到端实测值。

| # | 改动 | 独立收益 | 性质 |
| --- | --- | --- | --- |
| 1 | `training.compile: true` | 8 卡 1.32×（468.8 → 355.3 ms） | 纯性能 |
| 2 | `model.fast_attention: true` | 显存 −13.5%；速度 1.038× | 纯性能 |
| 3 | `model.stem_norm: group` | 速度中性 | **破坏 checkpoint 兼容** |
| 4 | `data.max_frames: 13` | 8 卡 1.230× | 数据集特定，依赖 #3 |
| 5 | `data.num_workers: 2` | epoch 1.34× | 环境特定（暖 cache） |

### 2.1 torch.compile

```yaml
training:
  compile: true
  compile_mode: max-autotune-no-cudagraphs
```

8 卡实测（frames=13 norm=group bs=4）：

| 模式 | Step | 首步编译 |
| --- | ---: | ---: |
| eager | 468.8 ms | — |
| `default` | 409.1 ms | ~85 s |
| `max-autotune-no-cudagraphs` | 355.3 ms | ~590 s |

`max-autotune` 比 `default` 多花约 500 s 一次性编译，换 1.151×。改代码时用
`default`，正式跑用 `max-autotune-no-cudagraphs`。步间无重复编译（step 1–5 稳定在
432–437 ms）。

**不要用不带后缀的 `max-autotune`**：它会启用 CUDA graphs，在本项目的 DDP 下捕获阶段
直接失败（`cudaErrorStreamCaptureInvalidated`）。

compile 包在 DDP **外面**，让 DDPOptimizer 在梯度 bucket 边界切图，保住通信/计算
overlap。包装层次是 `OptimizedModule → DDP → AEFModel`——这也是为什么必须先修
checkpoint 解包（见 3.1）。

数值：compiled vs eager，`kappa=0` 时 max|diff| 2.238e-04，开采样时 6.660e-05。
差异来自浮点累加顺序而非 RNG 分歧，且比 bf16 自身 3.9e-03 的分辨率低一个数量级。

### 2.2 fast_attention

```yaml
model:
  fast_attention: true
```

用 `F.scaled_dot_product_attention` 手写实现替换 `nn.MultiheadAttention`。后者支持
cross-attention 并返回注意力权重，这里都用不到，而这份通用性在本模型的 shape（很多条短
序列，而非少数长序列）下有真实开销。单卡 A800、bf16 autocast、仅前向：

```text
time_attn  (4096 seqs x len  48 x dim 256): 3.78 -> 1.47 ms  (2.56x)
space_attn ( 192 seqs x len 256 x dim 256): 1.83 -> 0.36 ms  (5.13x)
```

端到端只有 1.087×（不开 compile）、1.038×（开 compile）。Amdahl：attention 只占
7.7% 参数量，且 compile 已经吸收了约 56% 的胶水开销。

**真正的理由是显存**：SDPA 从不物化注意力矩阵，峰值 28.38 → 24.56 GB（−13.5%），这是
compile 拿不到的。

等价性：fp32 下 max|diff| 5.1e-07。参数名（`in_proj_weight` / `in_proj_bias` /
`out_proj`）与 `nn.MultiheadAttention` 保持一致，state_dict key 不变，旧 checkpoint
`strict=True` 可加载。

### 2.3 stem_norm: group ⚠️ 破坏 checkpoint 兼容

```yaml
model:
  stem_norm: group
```

**这一项不为速度**（单独测 500.5 vs 501.5 ms，在 3.5 ms 抖动内），它是为了让 #4 在数学上
站得住。

`SensorEncoderBank.forward` 把全部 T 个帧槽折进 batch 维，包括全零的 padding 槽，所以
BatchNorm 的批统计量是在真实帧和 padding 帧的混合上算的。这让 `max_frames` 从性能开关
变成了收敛开关：16 → 13 让 loss 变化 |dloss| 8.3e-02，而把 BN 移出路径后同一改动只剩
9.5e-07——足以把原因定在 BN 而非帧数本身。

全国尺度下 padding 比例随地区变化（云量、重访、传感器可用性），所以这不只是噪声，而是归一化
统计量里一个与地理相关的偏差。

GroupNorm 按样本在通道分组内归一化，padding 槽无法进入真实帧的统计量。

**代价**：丢弃 18 个 BatchNorm running-stat key（`missing=0, unexpected=18`，参数量
不变仍为 28.7189M）。`outputs/aef_hyh_yajiang_v1_2/` 下的权重**无法**加载进当前配置，从这里
开始的训练形成新的谱系。回退：`stem_norm: batch` + `max_frames: 16`。

### 2.4 max_frames: 13 ⚠️ 数据集特定

```yaml
data:
  max_frames: 13   # 依赖 model.stem_norm: group
```

全量 manifest 核对：1708 条记录在 s2/s1/landsat 三个源上**都恰好 13 帧**（直方图
`{13: 1708}`，无一条超过 13）。所以槽位 14–16 在结构上恒为空，18.75% 的时间轴计算跑在
保证为零的数据上。

8 卡 1.230×（501.5 → 407.7 ms）。比单卡的 1.139× 更大，因为 all-reduce 不被 compile
优化，它在 step 中的占比上升了。

**13 是这份 manifest 的属性，不是普适常数。** 全国尺度下帧数按地区变化，届时需要改成
变长打包（variable-length packing）而不是换一个更小的常数。

### 2.5 num_workers: 2

```yaml
data:
  num_workers: 2   # 每 rank；8 卡共 16 个，不是 8 个
```

原来每 rank 8 个 worker，8 卡就是 64 个 worker 跑在 64 个物理核上。8 卡实测：

| num_workers | loader 等待 | epoch | step |
| ---: | ---: | ---: | ---: |
| 8 | 7.71 s | 27.0 s | 350.9 ms |
| 4 | 1.70 s | 21.0 s | 350.3 ms |
| **2** | **0.75 s** | **20.1 s** | 350.2 ms |
| 1 | 2.58 s | 22.4 s | 349.5 ms |

nw=1 比 nw=2 更差，说明存在真实最优值，不是「越少越好」。step 时间四臂一致，这是干净的
对照——改动作用在输入路径而非计算。

竞争是超线性的：只跑 loader 的一遍，8 rank × 8 worker 用了 34.52 s，而单 rank 做
1/8 的工作只要 3.68 s——8 倍的工作量花了 9.37 倍时间，总吞吐是**下降**而不是持平。

还有一个没预料到的收益：64 个 worker 同时在饿死那个负责下发 CUDA kernel 的主进程。仅仅
减少 worker 数，epoch 内计算时间就从 23.14 s 降到 19.18 s（1.21×）。

经验法则：总 worker 数约 16，即 `num_workers ≈ 16 / nproc_per_node`。

**暖 cache 警告**：12.64 GB 数据集完全装进 1056 GB 内存的 903 GB page cache，0.904
ms/文件是内存速度不是存储速度，这些 worker 只在并行化 CPU 变换。冷读时它们还要隐藏 IO
延迟，最优值会上移——**全国尺度请重新测量，不要沿用 2**。

## 3. 附带修复

### 3.1 checkpoint 解包（compile 的前置条件）

`torch.compile(DDP(model))` 的嵌套是 `_orig_mod → module → model`，而
`Trainer._state_dict()` 原来只剥 `.module`。compile 后的运行会把每个 key 都写成带
`_orig_mod.` 前缀，这种 checkpoint 无法加载进未 compile 的模型——而故障要到 load 时才
暴露，离产生它的那次训练已经很远。

`_unwrap()` 按任意顺序剥掉两层包装，`_state_dict()` 与 `load_checkpoint()` 都用它。

必须**先于**启用 compile 落地，否则第一次 compile 训练就会静默写出加载不回来的 checkpoint。

### 3.2 DDP 梯度 stride 警告

compile 下每个 rank 报一次：

```text
grad.sizes() = [256, 768, 1, 1], strides() = [768, 1, 768, 768]
bucket_view.sizes() = [256, 768, 1, 1], strides() = [768, 1, 1, 1]
```

H=W=1 时这两组 stride 描述的是**完全相同的字节**——H、W 索引恒为 0，它们的 stride 永不
参与寻址。这是退化形状下的元数据不一致，不是真实布局差异：inductor 给这些梯度选了
channels_last，而 DDP 早已按连续布局给参数建好了 bucket，reducer 逐元素比 stride、不做
等价判断。

DDP 用 `as_strided(param.sizes(), param.strides())` 建 bucket 视图，所以在 DDP 包装
**之前**把 1×1 conv 权重转成 channels_last，bucket 就会匹配 inductor 的产出。四臂对照
（8 卡、当前配置）：

| 臂 | step | 峰值显存 | 警告 |
| --- | ---: | ---: | --- |
| none | 351.5 ms | 20.86 GB | 有 |
| `gradient_as_bucket_view=True` | 349.5 ms | 20.86 GB | **仍有** |
| channels_last | 352.8 ms | 20.86 GB | 无 |
| 两者都开 | 349.8 ms | 20.86 GB | 无 |

常被推荐的 `gradient_as_bucket_view=True` **消不掉这个警告**：bucket 视图仍是按参数的
连续 stride 建的，inductor 的 channels_last 梯度照样要拷进去。

**诚实记账：这项改动买不到任何可测收益。** step 时间四臂落在 349.5–352.8 ms、单臂抖动
2.0–4.7 ms，峰值显存到 0.01 GB 都一样。落地它是因为转换已验证为惰性，而警告会在每次运行时
持续吸引注意力。数值（`kappa=0` 关掉 vMF 采样以隔离浮点累加顺序与 RNG 分歧）：max|diff|
5.960e-08，相对 embedding 尺度 3.836e-01，比 bf16 的 3.9e-03 低四个数量级。

开关：`training.channels_last_1x1_conv`（默认 true）。

## 4. 当前瓶颈

epoch 20.1 s 中，epoch 内计算 19.18 s——**约 95% 计算受限**。输入侧和 H2D 已经没有
有意义的空间了（loader 等待 0.75 s，H2D 0.25 s）。

已测但未采纳：

- **batch_size**：8 卡吞吐在 bs=4/8/12 下几乎持平（78.5 / 80.4 / 80.9 patches/s，
  3 倍区间只涨 3.1%），而 epoch 时间反而变差（28.1 / 31.1 / 35.3 s），bs=16 OOM。
  step 时间随 batch 近乎线性增长，是 GPU 在 bs=4 已经饱和的特征。
- **naive channels_last**（全模型）：0.80×，更慢。

尚未攻击：

- **数据搬运**：28.6% 的时间花在零 FLOP 的数据搬运上（NCHW↔NHWC 占 9.4%），MFU 24.4%。
  需要重组 `STPBlock` 的 `reshape`/`permute`，而不是简单套 `channels_last`。
- **checkpoint 保存**：实测每 epoch 1–3 s（345 MB/文件，约 230 MB/s）。之前担心它在
  20 s 的 epoch 上会变成最大单项，实测否定了这个担心。注意日志时间戳只有秒级分辨率，这是
  粗测。
- **prefetch_factor**：nw=2 时 step 抖动 292.4 ms（nw=8 时 2.6 ms），中位数不受影响
  （350.2 ms），说明偶有供给停顿。提高 `prefetch_factor` 也许能补上。

## 5. 复现与回退

### 复现基线（v1.2 原始行为）

```yaml
model:
  fast_attention: false
  stem_norm: batch
data:
  max_frames: 16
  num_workers: 8
training:
  compile: false
```

此时可加载 `outputs/aef_hyh_yajiang_v1_2/checkpoints/*.pt`。

### 迭代开发时

```yaml
training:
  compile_mode: default   # 编译 85 s 而非 590 s
```

### 换硬件/换规模时必须重测

| 项 | 是否需要重测 |
| --- | --- |
| `compile` / `fast_attention` | 否，通用 |
| `stem_norm: group` | 否，全国尺度下更重要 |
| `max_frames` | **是**，由数据决定 |
| `num_workers` | **是**，与核数、内存带宽、存储速度都相关 |
| `batch_size` | 换 A100/H100 后可重试 |

## 6. 测量脚本

全部提交在 `scripts/`，本文档每个数字都出自其中之一。

```bash
# 8 卡分臂对比
bash scripts/run_bench_ddp8.sh

# compile 模式对比
bash scripts/run_bench_modes.sh

# DDP stride 修复四臂验证
bash scripts/run_bench_grad_stride.sh

# 数值等价性
CUDA_VISIBLE_DEVICES=5 PYTHONPATH=.:scripts \
  /home/heyuhang/miniconda3/envs/hyh-dl/bin/python scripts/check_cl_equivalence.py --kappa 0
```

写新 benchmark 时沿用的约定：

- **显式指定解释器** `/home/heyuhang/miniconda3/envs/hyh-dl/bin/python`。系统的
  `/usr/bin/python` 有 onnx 1.16 / protobuf 4.24 冲突，会让 `torch._dynamo` 导入直接
  崩溃（`onnxruntime.py` 只挡了 `ImportError`，但实际抛的是 `TypeError`）。
- **一臂一个全新 torchrun**，避免 compile 状态泄漏；`bench_grad_stride.py` 还额外依赖
  这一点，因为 `TORCH_WARN_ONCE` 每进程只报一次。
- **停表前先 `torch.cuda.synchronize()`**，取多次中位数，并**同时报告抖动**——小于抖动的
  差异不携带信息。
- **必须有对照臂**。

两个已知的测量缺陷已写在脚本注释里：`bench_ddp8.py` 对各分量分别做 `allreduce_max`，
求和后不对应任何一个真实 rank（分量有效，和无意义）；`bench_input_pipeline.py` 第 2 节
的读/变换拆分被前一次 `ds[i]` 的 page cache 预热污染，偏低。
